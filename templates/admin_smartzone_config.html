4. CoA (Change of Authorization)

The portal sends RFC 5176 Disconnect-Message packets to your SmartZone controller so a freshly approved/denied client picks up its new status on reassociation instead of waiting out its existing session.

CoA Host
{{ coa_host or '(not set)' }}

CoA Secret
same as RADIUS shared secret (Ruckus convention)

SmartZone-side configuration — on the AAA Authentication Service profile you created in step 1:

  • Enable Backup RADIUS > Enable Backup RADIUS support OFF (unless you have a real backup).
  • In RFC 5580 Out of Band Location Delivery leave defaults.
  • Make sure the WLAN's RADIUS Options → NAS ID Type is set so the portal's NAS-IP-Address attribute matches what SmartZone expects. The portal sends NAS-IP-Address = {{ coa_host or '(coa_host)' }}.
  • SmartZone listens for CoA on UDP 3799 on the controller's cluster control IP, not the management IP. {{ coa_host or '(set COA_HOST)' }} must be reachable on that port from this appliance.

5. Service-user permissions

The SmartZone account in SZ_USERNAME needs permission to disconnect clients via the Public API. Without it, the portal's first-choice kick path returns 403 Permission denied (Lack of admin privilege) and falls back to CoA-RADIUS.

Administration → Admins and Roles → Administrators → edit the service user. Assign a role with at least Wireless LANs → Modify and Clients → Manage / Disconnect. The default Network Administrator role covers this; a read-only operator role does not.

Quick test from a shell on this box:

curl -sk -X POST "https://<sz-host>:8443/wsg/api/public/v11_1/serviceTicket" \
  -H 'Content-Type: application/json' \
  -d '{"username":"'"$SZ_USERNAME"'","password":"'"$SZ_PASSWORD"'"}'
# Take the serviceTicket from the reply, then:
curl -sk -X POST "https://<sz-host>:8443/wsg/api/public/v11_1/clients/disconnect?serviceTicket=<ticket>" \
  -H 'Content-Type: application/json' \
  -d '{"mac":"AA:BB:CC:DD:EE:FF","apMac":"<ap-mac>"}'

A 200/204 means the role is right. A 403 with errorCode 211 means it isn't.

Troubleshooting

Captive portal keeps reloading after I approve a device.

The DB approval worked, but the running client session wasn't kicked — so the device is still on its old (pending) session. Either fix the service-user role (above) so the SmartZone API path works, or get CoA-RADIUS working (check NAS IP, UDP 3799 reachability, and that the shared secret matches what SmartZone has on its CoA receiver). Until one of those paths succeeds, end users have to disconnect from the Wi-Fi and rejoin to pick up the new status.

CoA Disconnect timeout (no reply from {{ coa_host or '...' }}:{{ coa_port }}).

SmartZone never sent an ACK/NAK. Common causes: (a) {{ coa_host }} isn't actually a SmartZone CoA listener (use the cluster-control IP, not the management IP); (b) UDP 3799 is firewalled between this box and SmartZone; (c) shared secret mismatch — fix it in the wizard or .env.

Android devices connect to the SSID but never show the captive portal.

Android probes connectivitycheck.gstatic.com/generate_204 and clients3.google.com/generate_204 to decide whether the network is open or behind a portal. If those URLs reach Google through the walled garden (e.g. because the WLAN has *.gstatic.com or *.google.com whitelisted), Android gets the 204 and assumes the network is open — no portal prompt, no sign-in screen. Replace the wildcards with the specific subdomain list above. iOS uses captive.apple.com and Windows uses www.msftconnecttest.com; we deliberately don't include those either, so all three platforms trigger their captive-portal UI the same way.

Need to change any of these? Click Re-run setup wizard on the Settings page.
